ER-PLATFORM-001

Interview prep — the full stack, the real problems hit while building it, and prepared answers.

Multi-tenant entity resolution SaaS for Indian school records. Solo-built: schema and RLS design, the full ML pipeline, Celery orchestration, the FastAPI layer, and a Next.js frontend. All facts below (test counts, versions, migration count) were re-verified against the running project on 2026-09-21, not recalled from memory.

1. The 30-second answer

Say this "It's a multi-tenant SaaS platform that deduplicates Indian school records — customers upload a CSV where the same school appears several times spelled differently, and the system decides which rows are the same place. The hard constraint was doing that without comparing every record to every other one, which is quadratic at 50,000 rows, and doing it with hard tenant isolation since multiple customers share one database. I built the schema and row-level security, the ML pipeline — a cold-start classifier, embeddings, vector blocking, probabilistic matching — the Celery orchestration, the FastAPI layer, and a Next.js review UI. 242 tests, all passing, run against real Postgres/Redis/Celery containers, not mocks."

3. Architecture, in one diagram

CSV upload (202 Accepted, returns immediately)
  │
  ├─▶ INGEST     parse CSV in chunks, store rows verbatim as JSONB
  ├─▶ CLASSIFY   XGBoost: Valid / Junk / Missing_Context (weak-supervision cold start)
  ├─▶ EMBED      normalise text → 2×768-dim vectors per record (Valid rows only)
  ├─▶ BLOCK      pgvector HNSW nearest-neighbour search → candidate pairs → clusters
  ├─▶ MATCH      Splink Fellegi–Sunter scoring on every pair inside every cluster
  └─▶ GATE       route by the tenant's own thresholds:
        ≥ 0.950 → AUTO_MERGED   (no external call)
        ≥ 0.750 → PENDING_API   (Google Places validation, cached + rate-limited)
        < 0.750 → PENDING_REVIEW (a human decides)

Nine Celery queues, one per stage, independently scaled. Stages hand off through Postgres, not through Redis payloads — a 50k-row job produces roughly a million candidate pairs, and routing those through the broker would turn it into a data channel it was never sized for. Postgres Row-Level Security enforces tenant isolation independently of application code, so a forgotten WHERE tenant_id = ? is a bug caught at the database, not a breach.

4. War stories — real bugs, ready for "tell me about a hard problem"

Each of these is a genuine STAR answer: found under real load (mostly the Docker-backed integration suite or a live click-through, not a mock), with a root cause and a verified fix. Pick 2–3 depending on how technical the interviewer is — the RLS one and the Windows event-loop one are the strongest general-audience stories; the deadlock and the Splink calibration one are the strongest for a backend-focused interviewer.

War story 1 severity: high
Row-Level Security caught a bug I didn't know I had — 5 of 6 write paths never set tenant_id
Situation
I'd built two independent tenant-isolation layers on purpose: the application always scopes queries by tenant, and Postgres RLS enforces the same rule at the database level as a backstop. The policy has a WITH CHECK clause, not just USING — it governs what a query is allowed to write, not just what it can see.
Task
Run the first real end-to-end pipeline test against live Docker containers instead of mocks.
Action
The very first insert failed with "new row violates row-level security policy". I traced every write site in the codebase and found five of six — jobs, school_records, clusters, cluster_members, human_feedback — never set tenant_id explicitly. They relied on the session being tenant-bound, which governs what you can see, but the WITH CHECK clause requires the column to be set correctly on the row itself.
Result
Fixed all five sites, then wrote an integration test that inserts through the real API and confirms the row lands with the right tenant. This would have made every single upload fail in production, and no unit test would ever have caught it — you need a real Postgres evaluating a real policy.
War story 2 severity: high
A self-inflicted deadlock that hung a worker for 10+ minutes, with no error
Situation
Every Celery stage wraps its work in a try/except that marks the job FAILED on error, so a failure is always diagnosable from Postgres alone, per the design requirement.
Task
The error handler opens a second database session to write the failure — because the first session's transaction is about to roll back, and writing inside it would roll the failure message back too.
Action
What I missed: the failing transaction still held a row lock on that exact jobs row (from an earlier status update in the same request). The second session tried to update the same row and blocked on the lock. I caught it live with pg_stat_activity — one session idle in transaction, the other waiting on Lock/transactionid for over ten minutes. Postgres's own deadlock detector never fired, because the first session wasn't waiting on a lock at all — it was waiting on the client. No cycle, no detection, just a permanent hang.
Result
Fixed by rolling back the failing transaction before opening the second session. Added a hard pytest-timeout of 120 seconds to the whole test suite afterward, specifically so a regression like this fails loud instead of hanging CI silently.
War story 3 severity: high
Windows made the entire async API non-functional, and no test caught it
Situation
242 tests passing, mypy and ruff clean, backend "done." First real HTTP request from the frontend to the API — every database-backed route returned 500.
Task
Diagnose psycopg.InterfaceError: Psycopg cannot use the 'ProactorEventLoop' to run in async mode.
Action
Uvicorn hardcodes ProactorEventLoop on Windows, and psycopg's async mode refuses to run on it. My first fix — setting the asyncio event-loop policy in the app module — silently did nothing, because uvicorn passes an explicit loop_factory to asyncio.run(), which bypasses policies entirely. The working fix is a CLI flag: --loop asyncio:SelectorEventLoop, which is uvicorn's own escape hatch and happens to be the default behaviour on Linux/macOS anyway, so one command works everywhere.
Result
No test suite would have caught this without cost: the unit tests exercise the auth boundary only (never touching the DB), and the integration tests use Celery's sync engine. Only a real HTTP request through the async engine exposes it — which is exactly why I manually drove the app through the browser-equivalent flow before calling it done, rather than stopping at green tests.
War story 4 severity: medium — correctness
A probabilistic matcher that ran clean and was silently useless
Situation
Splink's matcher needs three fitting steps: estimate u (agreement rate among non-matches), estimate m (agreement rate among matches) by Expectation-Maximisation, and estimate the prior probability that two random records match at all.
Task
I implemented the first two and skipped the third as an apparent refinement.
Action
The model ran with no errors and ranked pairs in the right order — but genuine duplicates scored 0.043 and non-duplicates scored 0.000. Since auto-merge triggers at 0.950, nothing would ever have auto-merged, ever, on any data. This is the dangerous kind of bug: it produces plausible-looking, silently wrong output rather than an error.
Result
Adding the missing prior-estimation step moved genuine duplicates to 0.87–0.91. Lesson I take into interviews: a model that runs without exceptions is not a model that is correct — test the actual output values, not just that the pipeline completes.
War story 5 severity: medium — data integrity
The multilingual model was chosen for Devanagari text, then a regex silently destroyed it
Situation
The embedding model was deliberately chosen to be multilingual, because Indian school names arrive transliterated inconsistently and sometimes not transliterated at all.
Task
Write the text normaliser that runs before embedding — strip punctuation, expand abbreviations.
Action
My punctuation stripper kept "word characters" via \w and discarded the rest. Python's \w does not count Devanagari combining vowel marks as word characters, so केंद्रीय विद्यालय came back as a row of bare consonants — the exact text the multilingual model was chosen to handle, destroyed before it ever reached the model.
Result
Fixed by inverting the logic — name the punctuation to remove instead of naming the characters to keep. Caught by a test that asserted every Devanagari code point in the input survived normalisation, written specifically because "the model is multilingual" is a claim that needs its own test, not an assumption that falls out of the classifier tests passing.
War story 6 severity: medium — frontend
A feature that looked finished and never worked once, because of how browsers navigate
Situation
The CSV export button was a plain <a href="/v1/jobs/{id}/export">, deliberately not a fetch call — the reasoning being that a real browser navigation streams a 50,000-row file without ever buffering it in JS memory, which is correct.
Task
What that reasoning missed: a top-level browser navigation sends no Authorization header, and the backend route requires a bearer token.
Action
The button 401'd every single time — not intermittently. The steward's review page was replaced by the raw JSON body {"detail":"Missing bearer token"}, discarding their queue position. This was caught by an adversarial code-review pass I ran specifically to find issues like this — a reviewer traced the auth chain through four separate attempts to refute the claim and confirmed it every time.
Result
Fixed with a Next.js route handler that attaches the token server-side and pipes the response stream straight through — same memory property, the missing header fixed. Verified live: 401 before, 200 with a real streaming CSV after.
War story 7 severity: low but memorable
"It's up" was the wrong question — an HTTP 200 that meant nothing
Situation
I ran next build twice while next dev was live. Next.js shares the .next build directory between the two by default.
Task
The production build overwrote the dev server's chunk manifests mid-flight. The user reported the page "not opening."
Action
Every server-side check passed: the port was listening, server-side rendering returned HTTP 200 with valid HTML, the backend health check was green. The actual failure was invisible to curl: the browser was told to fetch main-app.js, the React runtime itself, and got a 404. Blank page, forever, with every "is it up?" check lying.
Result
Fixed by giving builds a separate output directory (.next-build) so the collision is structurally impossible, then proved the fix by deliberately rerunning the exact sequence that broke it. The lesson: for any client-rendered app, checking that HTML came back is not checking that the app works — check that its JS assets actually returned 200 too.

6. Design decisions an interviewer will probe

Why Postgres RLS instead of just filtering every query in application code?

Defense in depth. NFR was explicit: a single forgotten WHERE tenant_id = ? must not be a data breach. Application-level filtering is still the primary layer — RLS is the backstop that turns "someone missed a filter" into "the database rejected the write," which is exactly what happened in War Story 1.

Why blocking before matching, instead of scoring every pair?

Quadratic cost. 50,000 rows is 1.25 billion pairs. Blocking uses cheap vector similarity to cut that down to a few thousand plausible pairs before the expensive probabilistic scorer ever runs.

Why weak supervision for the classifier instead of collecting labels first?

Cold start — a brand-new tenant has zero labelled data on day one. Multiple cheap heuristic rules vote, and rows where they disagree are deliberately excluded from training rather than guessed at; those are exactly the rows that should go to a human first.

Why is the confidence gate three bands instead of a single threshold?

Cost and trust calibration. High confidence auto-merges for free. Mid-confidence pays for one external validation call rather than either auto-merging on a shaky score or burning a human reviewer's time on something a cheap API call could settle. Low confidence always goes to a human — the system never guesses on a case it isn't sure about.

Why hand-write Alembic migrations instead of autogenerating them?

Two things autogenerate doesn't round-trip reliably: HNSW indexes with operator classes and build parameters, and the RLS policies themselves, which are security-critical enough to want reviewed as literal SQL rather than trusted to a diff tool.

Why does the frontend proxy through Next.js instead of calling FastAPI directly?

The backend has no CORS middleware, so a direct browser call from a different origin is blocked before FastAPI ever sees it. Proxying makes every call same-origin, and leaves adding real CORS as a deliberate production decision — an allow-list of real origins — rather than something loosened for local convenience.

8. Questions to ask them back

Turn it around Good, genuine questions — not just "wrap-up" filler:

  • "How do you handle multi-tenant data isolation — is it RLS, separate schemas, separate databases per tenant?"
  • "What's your team's answer to 'the pipeline ran with no errors but the output was wrong' — do you have output-value assertions in CI, or mostly exception-based tests?"
  • "How do you catch platform-specific bugs like the Windows event-loop one — do you run CI on more than one OS, or is dev/prod parity enough?"

9. If they ask what you'd do differently

Honest answer, prepared "Three things. First, I'd write the output-value assertions — not just 'does it run' — earlier for the ML stages; the Splink calibration bug should have been caught by a test that checks a known duplicate scores above some floor, not just by manual inspection. Second, I'd stand up the Docker integration suite before writing five write-paths that forgot tenant_id, not after — the sooner you're testing against a real database, the fewer of these compound. Third, the mid-confidence Google Places validation band is routing logic only; the actual external call behind it is unimplemented — that's the most honest gap in the project."
